**ADR: 2026-11.7 - Организация API**

**Дата:** 16 ноября 2026 г.

**Статус:** Принято

**Контекст:**

API используется веб-клиентом, мобильным приложением и админкой. Нужна четкая документация и стабильность.

**Рассмотренные варианты:**

1. **RESTful API:** Просто в разработке, но сложно масштабировать, риски потери данных при сбое сервера, высокая нагрузка на CPU/RAM при отдаче файлов.
2. **GraphQL:** Дешевое хранение, высокая доступность, CDN-интеграция, разгрузка основного сервера.
3. **gRPC:** Крайне не рекомендуется из-за низкой производительности и сложности резервного копирования.

**Решение:**

Выбран RESTful API.

**Обоснование:**

- **Ресурсная природа домена:** Сущности «Парковка», «Бронирование», «Отзыв» имеют четкие CRUD-операции и связи. REST с его глаголами HTTP и статус-кодами интуитивно отражает бизнес-логику, в отличие от GraphQL, где гибкость запросов избыточна для стандартных операций аренды.
- **Кэшируемость геозапросов:** Поиск парковок на карте — read-heavy операция. HTTP-семантика REST позволяет кэшировать ответы на уровне CDN/браузера/Redis по URL и заголовкам, что невозможно в GraphQL (POST-запросы не кэшируются нативно). Это напрямую влияет на отзывчивость карты.

**Недостатки решения:**

- Over-fetching/under-fetching данных (клиент получает либо лишнее, либо недостаточно), множество эндпоинтов при сложных связях.

**Последствия:**

- Строгое версионирование API (/api/v1/). Валидация входных данных через сериализаторы.
