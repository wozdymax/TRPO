**ADR: 2026-11.7 - Выбор способа кэширования часто запрашиваемых данных**

**Дата:** 16 ноября 2026 г.

**Статус:** Принято

**Контекст:**

Поиск парковок и чтение профилей — read-heavy операции. Геозапросы дорогие.

**Рассмотренные варианты:**

1. **Redis:** In-memory, богатые структуры данных, pub/sub.
2. **Memcached:** Простой key-value, быстрее для простых ключей, но беднее функционал.
3. **Локальный кэш (in-process):** Быстро, но несогласованность между инстансами.

**Решение:**

Выбран Redis.

**Обоснование:**

- **Унификация инфраструктуры:** Redis уже выбран (брокер Celery) Использование единого in-memory хранилища для кэша, очередей и auth исключает развертывание Memcached или отдельного кэш-слоя, снижая операционную сложность.
- **Богатые структуры для геокэширования:** Redis поддерживает GeoHash, Sorted Sets и TTL на уровне ключей. Можно кэшировать результаты bounding-box запросов с автоматической инвалидацией при изменении статуса парковки. Memcached предлагает только простой key-value без нативной гео-поддержки.

**Недостатки решения:**

- Over-fetching/under-fetching данных (клиент получает либо лишнее, либо недостаточно), множество эндпоинтов при сложных связях.

**Последствия:**

- Стратегия инвалидации кэша при изменении статуса парковки/бронирования. Мониторинг hit-rate.
