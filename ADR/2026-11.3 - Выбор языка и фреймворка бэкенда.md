**ADR: 2026-11.3 - Выбор языка и фреймворка бэкенда**

**Дата:** 16 ноября 2026 г.

**Статус:** Принято

**Контекст:**

Платформа требует надежной обработки транзакций (бронирования, платежи), работы с геоданными и быстрой разработки бизнес-логики (календари, рейтинги). Команда нуждается в зрелой экосистеме для реализации модульного монолита.

**Рассмотренные варианты:**

1. **Python/Django:** Зрелая экосистема, встроенный ORM, отличная поддержка GeoDjango (PostGIS), быстрая разработка. Минус: ниже производительность CPU-bound задач.
2. **Go/Gin:** Высокая производительность, строгая типизация. Минус: отсутствие полноценного ORM «из коробки», медленнее разработка сложной бизнес-логики.
3. **Node.js/NestJS:** Единый стек с фронтендом, хорошая асинхронность. Минус: слабее работа с тяжелыми геозапросами и транзакционной целостностью по сравнению с Python/Java.
4. **Java/Spring:** Энтерпрайз-стандарт, строгая типизация. Минус: высокий порог входа, избыточность для стартапа.

**Решение:**

Выбран Python + Django REST.

**Обоснование:**

- **GeoDjango:** Лучшая в классе интеграция с PostGIS для поиска парковок на карте.
- **Скорость разработки:** Встроенный Admin, ORM, аутентификация, библиотеки для платежки ускоряют MVP.
- **Соответствие архитектуре:** Django идеально ложится на концепцию модульного монолита (через Django Apps).

**Последствия:**

- Необходимо следить за качеством кода и типизацией (использовать mypy/pydantic). Для высоконагруженных участков (поиск) возможно вынесение в отдельные воркеры или оптимизация через кэширование.
